Current Audio + Visualizer Pipeline
-------------------------

filesrc → decodebin → audioconvert → audioresample → tee
           ├─ queue_audio → volume → autoaudiosink
           └─ queue_video → goom → videoconvert → gtksink

Notes:
- audioconvert + audioresample are placed before the tee.
- This ensures that both the audio sink and the goom visualizer
  receive audio in the proper PCM format (e.g., 16-bit).
- Good for audio + visualizer scenario.

Reusable Audio + Visualizer Pipeline
-------------------------

filesrc → decodebin → tee
           ├─ queue_audio → audioconvert → audioresample → volume → autoaudiosink
           └─ queue_video → audioconvert → audioresample → goom → videoconvert → gtksink

Notes:
- Both audio and visualizer branches have their own audioconvert + audioresample.
  → Ensures audio format is correct for both sinks.
- Audio branch: volume → autoaudiosink
- Visualizer branch: goom → videoconvert → gtksink
- Modular design allows reusing the **audio branch** for audio-only or audio+video pipelines.
- Goom visualizer branch is independent and still receives proper PCM audio.


-------------------------

Reusable Audio + Visualizer Pipeline (with Queues after gooom element)
-------------------------

filesrc → decodebin → tee
           ├─ queue_audio → audioconvert → audioresample → volume → autoaudiosink
           └─ queue_visualizer → audioconvert → audioresample → goom → queue_video_sink → videoconvert → gtksink
           
 queue_video_sink:
    - Separates gtksink (video sink) from goom.
    - Ensures GUI sink slowness doesn’t block audio or visualizer threads.
    
    
Design Advantages:
------------------
- Modular and reusable.
- Audio branch works standalone.
- Visualizer branch independent, preventing audio/video blocking.
- Easy to extend for audio-only, audio+visualizer, or audio+video pipelines.

Problem without a queue after goom:
-----------------------------------
1. Blocking issue:
    - If gtksink is slow (e.g., GUI update, vsync), it will block goom.
    - If goom is blocked, it will also block upstream elements like audioconvert or the tee.

2. Tee starvation:
    - The tee distributes data to multiple branches.
    - If one branch is slow and there is no queue, it can slow down or stall the other branch (e.g., audio).

3. CPU threading:
    - queue creates a new thread for that part of the pipeline.
    - videoconvert → gtksink can run independently from goom and upstream elements.

--------------------------------------------------------
✅️✅️Audio, Video, and Visualizer Bins
--------------------------------------------------------


filesrc → decodebin → tee
           ├─ queue_audio → audiobin
           │      (audioconvert → audioresample → volume → autoaudiosink)
           │
           └─ queue_visualizer → visualizer_bin → videobin
                  (audioconvert → audioresample → goom →) (-> queue_video_sink → videoconvert → gtksink)

1. Audio Bin (audiobin)
   ---------------------
   Elements:
       audioconvert → audioresample → volume → autoaudiosink
   Purpose:
       - Handles all audio processing.
       - Responsible for audio playback to the speakers.
       - Can be reused in audio-only or audio+video pipelines.

2. Video Bin (videobin)
   ---------------------
   Elements:
       queue_video_sink → videoconvert → gtksink
   Purpose:
       - Handles video rendering independently from audio or visualizer.
       - Queue separates GUI sink from upstream elements to prevent blocking.
       - Can be reused for video playback pipelines.

3. Visualizer Bin (visualizer_bin)
   --------------------------------
   Elements:
       audioconvert → audioresample → goom
   Purpose:
       - Processes audio for visualization.
       - Independent of audio and video branches to avoid pipeline blocking.
       - Ensures goom receives correct PCM audio format for visualization.
